# Intake Contract — Gateway JSON (v0.2)

**Status: implemented.** `POST /api/intake/v1/requests` validates against exactly these rules
(`app/Http/Requests/IntakeRequest.php`), and both worked examples in `tests/fixtures/intake/`
translate to Bundles that validate against the pinned IGs at **0 errors**.

The canonical JSON the gateway accepts from our own systems (`referral`, `telemedicine`).
It is **deliberately not FHIR**. Native systems speak business language; translating to
PH Core / eReferral is the gateway's job and no one else's.

Two rules drive the whole shape:

1. **The sender never names an endpoint.** It picks an opaque `hcpn_id` from the gateway's
   registry. Routing, credentials and transport stay inside the gateway, so onboarding a new
   destination changes nothing in the referral or telemedicine systems.
2. **The sender never sends FHIR.** No `resourceType`, no references, no `urn:uuid`.
   If a field here looks like FHIR, that's a leak and should be renamed.

---

## Endpoints

```
GET  /api/registry/v1/hcpn                  → the destination picklist
POST /api/intake/v1/requests                → submit
GET  /api/intake/v1/requests/{message_id}   → status
```

### `GET /api/registry/v1/hcpn`

Returns only destinations that can actually receive something. Add `?include_unreachable=1`
to see the full directory, `?accepts=referral` to filter by request type.

```json
{
  "data": [
    {
      "hcpn_id": "telemedicine-internal",
      "display_name": "Telemedicine Service",
      "city": "Internal",
      "nhfr_code": "DOH000000000000001",
      "hcpn_code": null,
      "accepts": ["referral", "telemedicine"],
      "deliverable": true
    }
  ],
  "count": 1
}
```

Endpoints and credentials are never in the response.

### `POST /api/intake/v1/requests`

| Code | Meaning |
|---|---|
| `202 Accepted` | Accepted, and delivery attempted. Body is the status object — check `status`. |
| `200 OK` | Duplicate `message_id` on an already-delivered referral. Returns the original result and does nothing else. |
| `409 Conflict` | The two national identifiers resolve to two different patients at the receiver. `OperationOutcome`. Nothing was sent. |
| `422` | Schema or business-rule failure. `OperationOutcome` with one issue per field. |
| `400` | Malformed JSON. |

Status object:

```json
{
  "message_id": "8c2d5b31-77af-4e0a-b1c6-2d9f4a83e510",
  "gateway_ref": "17",
  "status": "delivered",
  "request_type": "telemedicine",
  "destination": "telemedicine-internal",
  "attempts": 1,
  "task_id": "task-99",
  "service_request_id": "sr-42",
  "delivered_at": "2026-09-07T10:15:04+08:00",
  "last_error": null
}
```

`status` is one of `pending`, `sending`, `delivered`, `failed`.

**Retry is the sender's job, and that is deliberate.** The gateway stores no payload, so it
cannot rebuild a failed referral on its own. A `202` with `status: failed` means: nothing was
delivered, resubmit the same `message_id` when you want it retried. Because the id is the
idempotency key, resubmitting can never open a second referral.

## Envelope

```json
{
  "message_id": "0f1a5c8e-2b7d-4a91-9f3e-6c2d8b4a1e07",
  "sent_at": "2026-09-07T14:32:10+08:00",
  "request_type": "referral",
  "source": { },
  "destination": { },
  "patient": { },
  "clinical": { },
  "referral": { },
  "telemedicine": { },
  "attachments": [ ]
}
```

| Field | Req | Notes |
|---|---|---|
| `message_id` | ✅ | UUID, generated by the sender. **The idempotency key.** Also becomes `Task.identifier`, so the receiver can spot a duplicate too. |
| `sent_at` | ✅ | ISO 8601 **with offset**. A bare timestamp is rejected, not assumed to be Manila time. |
| `request_type` | ✅ | `referral` \| `telemedicine`. Selects which of the two blocks below is required. |

---

## `source`

```json
"source": {
  "system": "referral",
  "record_id": "REF-2026-004821",
  "facility_code": "3056",
  "facility_name": "Kalibo Health Center",
  "practitioner": {
    "family_name": "Reyes",
    "given_names": ["Maria", "Luisa"],
    "prc_license": "0123456",
    "role": "physician",
    "phone": "+639171234567",
    "email": "mreyes@example.ph"
  }
}
```

| Field | Req | Notes |
|---|---|---|
| `system` | ✅ | `referral` \| `telemedicine`. |
| `record_id` | ✅ | The native primary key. Travels as `ServiceRequest.requisition`, so either side can trace a referral to its source record. |
| `facility_code` | ✅ | Sending facility, DOH NHFR code. |
| `facility_name` | ⬜ | Used for `Organization.name`. Without it the facility is identified by code alone, which is still valid. |
| `practitioner.prc_license` | ✅ | The identifier the receiving end can actually verify. Keys the Practitioner and PractitionerRole upserts. |
| `practitioner.role` | ⬜ | Default `physician`. One of `physician`, `nurse`, `midwife`, `pharmacist`, `medical-technologist`, `laboratory-aide`, `dentist`, `dental-aide`, `optometrist`. |

---

## `destination`

```json
"destination": { "hcpn_id": "telemedicine-internal", "department": "cardiology" }
```

`hcpn_id` must exist in the registry **and be deliverable**. A facility that is listed but has
no endpoint is rejected with `422` rather than accepted into a queue that will never drain.

## `patient`

```json
"patient": {
  "identifiers": [
    { "type": "philsys",    "value": "7731-0812-4491-0326" },
    { "type": "philhealth", "value": "78-658064775-3" }
  ],
  "family_name": "Dela Cruz",
  "given_names": ["Juan", "Santos"],
  "suffix": "Jr.",
  "birth_date": "1985-03-14",
  "sex": "male",
  "mobile": "+639171234567",
  "address": {
    "line": "123 Rizal St., Purok 4",
    "barangay_psgc": "0600407013",
    "city_psgc": "0600407000",
    "province_psgc": "0600400000",
    "region_psgc": "0600000000",
    "postal_code": "1100"
  }
}
```

| Field | Req | Notes |
|---|---|---|
| `identifiers` | ✅ | **At least one of `philsys` or `philhealth`.** A `local` MRN alone is rejected — it means nothing to the receiver. |
| `birth_date` | ✅ | `YYYY-MM-DD`. |
| `sex` | ✅ | `male` \| `female` \| `other` \| `unknown` — administrative, maps to `Patient.gender`. |
| `address.*_psgc` | ⬜ | PSGC **codes**, not names. Emitted as `Coding` extensions; the wrong datatype here is a hard validation error. |

**Send both identifiers whenever you have them.** Policy is that triage records both. The
gateway enforces only "at least one", because the process for patients who have neither yet —
newborns above all — is not settled. Sending both is what lets the receiver's record converge:
whichever identifier they already know finds them, and the other is added to their chart.

## `clinical`

```json
"clinical": {
  "reason_text": "Chest pain on exertion, 3-week history",
  "notes": "Patient stable. ECG attached.",
  "encounter": {
    "class": "AMB",
    "status": "finished",
    "start": "2026-06-18T07:45:00+08:00",
    "end": "2026-06-18T08:25:00+08:00"
  },
  "diagnoses": [
    { "system": "icd10", "code": "I20.9", "text": "Angina pectoris, unspecified" }
  ],
  "vitals": [
    { "name": "Heart rate", "code": "8867-4", "value": 96, "unit": "/min", "taken_at": "2026-06-18T07:50:00+08:00" }
  ]
}
```

| Field | Req | Notes |
|---|---|---|
| `reason_text` | ✅ | The clinician's own words. Rides in `ServiceRequest.reasonCode.text` alongside the coded reason. |
| `encounter` | ⬜ | Only send it if a real clinical contact happened. The gateway will not invent one from the referral timestamp. |
| `diagnoses[].text` | ✅ | Required per entry. `system` may be `icd10`, `snomed` or `text`. **An uncoded diagnosis is accepted** — refusing a referral because the clerk had no ICD-10 handy would be worse for the patient. |
| `vitals[].unit` | ⬜ | **UCUM** (`/min`, `Cel`, `kg`, `mm[Hg]`). A LOINC-coded vital pulls in the base FHIR vital-signs profile, which requires a UCUM-coded Quantity. |
| `vitals[].value` | ✅ | A number becomes a Quantity. Anything else (`"180/110"`) becomes a string — see the caveat below. |

**Blood pressure caveat.** `"180/110"` is not a number, so it is emitted as a string value.
To get a proper systolic/diastolic Observation the native system has to send the two numbers
separately. Splitting the string here would be the gateway guessing at clinical data.

## `referral` — required when `request_type = "referral"`

```json
"referral": {
  "category": "emergency",
  "service_type": "procedure",
  "priority": "urgent",
  "service_requested": "Cardiology consultation",
  "specialty": "cardiology"
}
```

| Field | Req | Allowed |
|---|---|---|
| `category` | ✅ | `emergency` \| `outpatient` |
| `service_type` | ✅ | `consultation` \| `diagnostics` \| `procedure` \| `others` |
| `priority` | ⬜ | `routine` \| `urgent` \| `asap` \| `stat` (default `routine`) |

`category` and `service_type` are required because the IG binds `ServiceRequest.category` and
`.reasonCode` to closed value sets with exactly these members. There is no safe default the
gateway could pick for you — guessing "emergency" or "outpatient" on a clinician's behalf is
not a translation decision.

## `telemedicine` — required when `request_type = "telemedicine"`

```json
"telemedicine": {
  "modality": "video",
  "specialty": "internal-medicine",
  "priority": "routine",
  "preferred_windows": [
    { "start": "2026-09-09T09:00:00+08:00", "end": "2026-09-09T12:00:00+08:00" }
  ]
}
```

`modality` ∈ `video` | `audio` | `chat` | `store-and-forward`.

**Known lossiness.** `ERefServiceRequest` slices `occurrence[x]` closed on `occurrenceDateTime`,
so a *window* cannot be expressed structurally. The window's **start** becomes the occurrence
and the full window is written into the referral note. A human sees both ends; a machine sees
only the start. This is the concrete form of the open question about whether a telemedicine
consult belongs in `Appointment` rather than `ServiceRequest`.

## `attachments`

```json
"attachments": [
  { "title": "12-lead ECG", "content_type": "application/pdf", "url": "https://.../abc", "expires_at": "2026-09-14T00:00:00+08:00" }
]
```

**By reference only — never base64.** Accepted and validated, but not yet translated into
`DocumentReference`; that is queued behind confirmation that the native systems can expose a
fetchable URL at all.

## How this maps to FHIR

| Intake | FHIR / PH Core |
|---|---|
| `message_id` | `Task.identifier`, and the `ifNoneExist` key on the Task entry |
| `source.record_id` | `ServiceRequest.requisition` |
| `source.facility_code` | `Organization` · `https://fhir.doh.gov.ph/phcore/Identifier/doh-nhfr-code` |
| `source.practitioner` | `Practitioner` + `PractitionerRole`, both keyed on `https://prc.gov.ph/` |
| `destination.hcpn_id` | resolved via the registry → `Organization` (`ServiceRequest.performer`, `Task.owner`) |
| `patient.identifiers[philsys]` | `http://philsys.gov.ph/fhir/Identifier/philsys-id` |
| `patient.identifiers[philhealth]` | `http://philhealth.gov.ph/fhir/Identifier/philhealth-id` |
| `patient.address.*_psgc` | PH Core address extensions, **`Coding`** on `https://psa.gov.ph/classification/psgc` |
| `referral.category` | `ServiceRequest.category` (SNOMED, required binding) |
| `referral.service_type` | `ServiceRequest.reasonCode` (SNOMED, required binding) |
| `clinical.encounter` | `Encounter` |
| `clinical.diagnoses` | `Condition` → `ServiceRequest.reasonReference` |
| `clinical.vitals` | `Observation` → `ServiceRequest.supportingInfo` |
| whole request | `Bundle` (transaction) + `Provenance` targeting the ServiceRequest |

Regenerate the worked examples with:

```
php artisan fhir:build-referral tests/fixtures/intake/referral-kalibo.json \
    --out=tests/fixtures/fhir/generated-referral-bundle.json
php artisan fhir:validate tests/fixtures/fhir/generated-referral-bundle.json
```

## Still open

1. **Attachments** — do the native systems have a fetchable URL, or only files on disk?
2. **PSGC** — do they store codes, or only address text? If text, the gateway needs a lookup
   table, which is unscoped work.
3. **Telemedicine as `ServiceRequest`** — confirmed lossy for scheduling windows. `Appointment`
   is the alternative, but the IG does not profile it.
4. **Cancellation / amendment** — no verb for it yet. A sender cannot withdraw a delivered
   referral.
5. **Blood pressure** — needs the native systems to send systolic and diastolic separately.
